The rule catalog

Every rule ships with a risk statement, recommendation, and standards mapping. Browse all 65 below, or add your own — see CONTRIBUTING.md.

Admin And Debug Surface

ADMIN_ROUTE_NO_ROLE_CHECK

critical

Risk: An admin-labeled route that only checks for a valid session (not an admin role) can be reached by any authenticated user.

Fix: Require an explicit role, permission, or claim check (e.g. role === "admin") in every admin route, in addition to authentication.

DEBUG_ENDPOINT_EXPOSED

high

Risk: Debug/internal endpoints often skip auth and can expose environment details, internal state, or admin actions if left reachable after launch.

Fix: Remove debug/test routes before shipping, or gate them behind authentication and a non-production environment check.

SWAGGER_UI_EXPOSED_PRODUCTION

medium

Risk: Swagger/OpenAPI UIs left reachable in production hand attackers a full map of your API surface, including internal or undocumented-elsewhere endpoints.

Fix: Mount API docs routes only when NODE_ENV !== "production", or put them behind authentication.

INTERNAL_ENDPOINT_INFO_LEAK

medium

Risk: A /health or /status route that echoes back environment variables, config, or dependency versions gives attackers reconnaissance information for free.

Fix: Return a minimal { status: "ok" } from health checks; keep detailed diagnostics behind authentication.

AI

AI_FRONTEND_OR_UNBOUNDED

critical

Risk: Unprotected AI calls can leak API keys, enable abuse, and burn API spend quickly.

Fix: Keep AI keys server-side, require authentication, enforce per-user/IP/tenant rate limits, cap tokens/input/file size, and track cost per billing account.

AI_PROMPT_INJECTION_REVIEW

medium

Risk: LLM features can leak sensitive context or execute unsafe tool actions if prompts, retrieval, or tools are not constrained.

Fix: Add prompt-injection mitigations, tool authorization checks, data minimization, and disclosure in the privacy policy when prompts are sent to AI providers.

API And Authorization

AUTHZ_IDOR_POSSIBLE

critical

Risk: Users may access another user's or tenant's records by changing an ID in the URL or request body.

Fix: Scope every sensitive query by authenticated user, organization, or tenant in the database query itself.

API_AUTH_MISSING

high

Risk: Public API routes can expose data or trigger sensitive actions without a valid user session.

Fix: Require server-side authentication and authorization in every sensitive API route.

API_VALIDATION_MISSING

medium

Risk: Unvalidated input can lead to malformed data, injection risks, and unexpected application behavior.

Fix: Validate request bodies with Zod, Valibot, Joi, Yup, or equivalent schema validation before use.

OPEN_REDIRECT_UNVALIDATED

medium

Risk: Redirecting to a URL taken directly from a query parameter can be used for phishing or to bypass OAuth redirect_uri allowlists.

Fix: Validate redirect targets against an allowlist of internal paths or trusted domains before redirecting.

MASS_ASSIGNMENT_RISK

high

Risk: Spreading the raw request body into a create/update call lets attackers set fields they should not control, such as role, isAdmin, or plan.

Fix: Explicitly allowlist the fields copied from request input into database writes instead of spreading the full body.

API_RATE_LIMIT_MISSING_PUBLIC

medium

Risk: Endpoints without any rate limiting are vulnerable to scraping, credential stuffing, and cost-driving abuse at scale.

Fix: Add per-IP and per-account rate limiting (e.g. Upstash, express-rate-limit, a WAF rule) to public-facing API routes.

GRAPHQL_INTROSPECTION_ENABLED

medium

Risk: Introspection lets attackers enumerate your entire schema, including fields and mutations not exposed in your app's UI.

Fix: Disable introspection (and the GraphiQL/Playground UI) outside of development environments.

GRAPHQL_NO_DEPTH_LIMIT

medium

Risk: Without a depth or cost limit, a single deeply nested or highly repetitive GraphQL query can exhaust server resources — a denial-of-service vector unique to GraphQL's flexible query shape.

Fix: Add a depth-limiting or cost-analysis library (e.g. graphql-depth-limit, graphql-cost-analysis) to the server's validation rules.

NEXTJS_SERVER_ACTION_NO_AUTH

critical

Risk: A "use server" action is a public network endpoint even though it's called like a function — without an explicit auth check, anyone who discovers its action ID can invoke it directly, bypassing any UI-level gating.

Fix: Verify the session/user at the top of every Server Action that reads or writes sensitive data, exactly as you would in an API route.

Auth

AUTH_PASSWORD_HASHING_WEAK

critical

Risk: Weak password storage can lead to account takeover if the database is exposed.

Fix: Use Argon2id or bcrypt with a suitable cost factor, never plaintext or raw SHA/MD5 hashes.

AUTH_LOGIN_RATE_LIMIT_MISSING

high

Risk: Unthrottled login attempts allow credential stuffing and brute-force attacks.

Fix: Apply rate limits per IP and per account, track failed attempts, and add lockout/backoff controls.

AUTH_SESSION_EXPIRY_MISSING

medium

Risk: Long-lived or unbounded sessions increase impact after token theft.

Fix: Configure bounded session expiry, refresh-token rotation where relevant, and server-side logout invalidation.

AUTH_COOKIE_FLAGS_MISSING

medium

Risk: Cookies without HttpOnly, Secure, and SameSite controls are easier to steal or abuse.

Fix: Set HttpOnly, Secure, and SameSite=Lax or Strict for session cookies in production.

PASSWORD_RESET_RATE_LIMIT_MISSING

high

Risk: An unthrottled password-reset or forgot-password endpoint allows attackers to enumerate valid accounts or flood users with reset emails.

Fix: Apply per-IP and per-account rate limits to password reset requests, same as login.

CORS

CORS_WILDCARD_WITH_CREDENTIALS

critical

Risk: A wildcard Access-Control-Allow-Origin combined with Access-Control-Allow-Credentials: true lets any site read authenticated responses on behalf of a logged-in user.

Fix: Use an explicit allowlist of trusted origins instead of * whenever credentials are allowed.

CORS_ORIGIN_REFLECTED

medium

Risk: Reflecting the request Origin header back verbatim effectively disables CORS protection for every origin.

Fix: Validate the incoming origin against an explicit allowlist before echoing it back in Access-Control-Allow-Origin.

Cryptography

WEAK_RANDOM_TOKEN_GENERATION

high

Risk: Math.random() is not cryptographically secure and its output can be predicted, letting attackers guess session tokens, password-reset tokens, or API keys generated from it.

Fix: Generate tokens with crypto.randomUUID() or crypto.randomBytes() instead of Math.random().

CSRF

CSRF_PROTECTION_MISSING

medium

Risk: State-changing requests authenticated only by cookies can be triggered from another origin without a CSRF token or same-site defense.

Fix: Use SameSite=Lax/Strict cookies together with a CSRF token (double-submit cookie or synchronizer token) for state-changing routes, or rely on a framework's built-in CSRF middleware.

Database

SQL_INJECTION_RAW_QUERY

critical

Risk: String-built SQL can allow attackers to read, modify, or delete database data.

Fix: Use parameterized queries or ORM query builders. Never concatenate user-controlled data into SQL.

SUPABASE_RLS_NOT_CONFIRMED

medium

Risk: Without RLS policies, any authenticated (or anonymous, with the anon key) client can read or write every row in a Supabase table directly from the browser.

Fix: Enable Row Level Security on every table and add explicit policies scoping access to the authenticated user or tenant.

RESPONSE_MISSING_PAGINATION_LIMIT

medium

Risk: A findMany/list query with no take/limit can return an entire table to a single request, enabling resource-exhaustion and over-fetching more data than the caller should see.

Fix: Always cap list queries with a take/limit and offer pagination for anything that can grow unbounded.

Dependency

DEPENDENCY_NO_LOCKFILE

medium

Risk: Without a lockfile, dependency versions can drift between installs, pulling in unreviewed or vulnerable transitive updates.

Fix: Commit package-lock.json, pnpm-lock.yaml, or yarn.lock and install with --frozen-lockfile in CI.

DEPENDENCY_WILDCARD_VERSION

medium

Risk: * or latest version ranges can silently pull in breaking or malicious updates, including supply-chain attacks published under a trusted package name.

Fix: Pin dependencies to specific or caret-ranged versions and review updates deliberately.

DEPENDENCY_KNOWN_RISKY_PACKAGE

high

Risk: Some packages are deprecated, unmaintained, or have a documented history of supply-chain compromise; continuing to depend on them carries elevated risk.

Fix: Replace deprecated/unmaintained packages with actively maintained alternatives and run npm audit regularly.

POSTINSTALL_SCRIPT_RISK

medium

Risk: postinstall/preinstall scripts execute arbitrary code the moment npm install runs, and are a common vector for supply-chain attacks in compromised packages. Having one in your own project also means every contributor and CI runner executes it blindly.

Fix: Avoid install-time scripts where possible; if one is required, keep it minimal, reviewed, and version-controlled.

Headers And Transport

HEADERS_HTTPS_RUNTIME

medium

Risk: Missing browser security headers increase exposure to XSS, clickjacking, MIME sniffing, and data leakage.

Fix: Enforce HTTPS and configure HSTS, CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, and Permissions-Policy.

CONFIG_HTTP_URLS

medium

Risk: Plain HTTP URLs can leak traffic and break secure cookie/OAuth/webhook expectations.

Fix: Use HTTPS for production URLs, OAuth callbacks, payment webhooks, and API integrations.

CSP_UNSAFE_INLINE

medium

Risk: unsafe-inline/unsafe-eval in a CSP largely defeats its purpose as an XSS mitigation, since it allows the exact inline script execution CSP is meant to block.

Fix: Use nonces or hashes for required inline scripts instead of unsafe-inline, and avoid unsafe-eval entirely.

SOURCE_MAP_ENABLED_PRODUCTION

medium

Risk: Public source maps let anyone reconstruct your original source code, including comments, variable names, and any logic you intended to keep private.

Fix: Disable source maps for production builds, or upload them privately to your error-tracking provider instead of serving them publicly.

MISSING_SRI_EXTERNAL_SCRIPT

medium

Risk: A <script> tag pointing at a third-party CDN without an integrity attribute will execute whatever that CDN serves, including a compromised or tampered file, with no verification.

Fix: Add an integrity attribute (SRI hash) and crossorigin="anonymous" to third-party script tags, or self-host the dependency.

Infrastructure

INFRA_DOCKER_ROOT_USER

medium

Risk: Containers running as root increase the blast radius of a container escape or dependency compromise.

Fix: Add a non-root USER directive to the Dockerfile and drop unnecessary capabilities.

INFRA_DB_PORT_EXPOSED

high

Risk: Publishing database/cache ports (Postgres 5432, MySQL 3306, MongoDB 27017, Redis 6379) beyond the internal Docker network can expose data stores directly to the internet on misconfigured hosts.

Fix: Remove public port mappings for data stores in production compose files and restrict access to the internal network or a VPN/bastion.

TERRAFORM_PUBLIC_S3_BUCKET

critical

Risk: An S3 bucket with a public-read ACL or disabled public-access-block settings can expose every object in it to the internet, including user uploads or backups.

Fix: Keep buckets private by default and use signed URLs or a CDN with access controls for anything that needs to be public.

TERRAFORM_OPEN_SECURITY_GROUP

high

Risk: A security group ingress rule with 0.0.0.0/0 on an administrative port (SSH 22, RDP 3389) or a database port exposes that service to internet-wide scanning and brute force.

Fix: Restrict ingress CIDR blocks to known IP ranges or a VPN/bastion, never 0.0.0.0/0 for administrative or database ports.

Code Execution And Deserialization

CODE_EXECUTION_EVAL_USER_INPUT

critical

Risk: eval, new Function, or child_process.exec used near request input can allow full remote code execution if any user-controlled value reaches it.

Fix: Remove dynamic code execution entirely, or if unavoidable, use a strict sandbox and never pass unsanitized user input into it.

JWT

JWT_ALGORITHM_NOT_ENFORCED

critical

Risk: Verifying tokens without pinning the expected algorithm allows algorithm-confusion attacks (for example forging an HS256 token signed with a known public RS256 key, or an alg: none token).

Fix: Always pass an explicit algorithms allowlist to jwt.verify and reject tokens with alg: none.

JWT_SECRET_WEAK_OR_HARDCODED

critical

Risk: A hardcoded or short JWT secret can be brute-forced or leaked through source control, letting attackers forge valid tokens.

Fix: Load the signing secret from environment variables, use at least 32 bytes of entropy, and rotate it if it was ever hardcoded.

JWT_NO_EXPIRATION

high

Risk: Tokens signed without expiresIn remain valid forever, so a leaked token gives permanent access instead of a bounded window.

Fix: Always set expiresIn when signing a JWT, and pair it with refresh-token rotation if long-lived sessions are needed.

Logging And Monitoring

LOGGING_SECRETS_RISK

high

Risk: Logging tokens, passwords, full request bodies, or provider payloads can create a secondary data breach path.

Fix: Redact secrets from logs and avoid logging full request bodies, authorization headers, cookies, payment payloads, and AI prompts unless explicitly scrubbed.

MONITORING_ANOMALY_GAPS

medium

Risk: Without security and cost anomaly alerts, abuse can continue unnoticed after launch.

Fix: Add alerts for failed login spikes, repeated 401/403s, sequential ID access, AI spend spikes, webhook failures, admin access, and error-rate increases.

VERBOSE_ERROR_STACK_TRACE_TO_CLIENT

medium

Risk: Returning err.stack or a raw error message to the client can leak file paths, library versions, query fragments, or other internals useful for an attacker's reconnaissance.

Fix: Log the full error server-side, and return a generic error message to the client.

OAuth

OAUTH_STATE_PARAM_MISSING

medium

Risk: Without a state parameter, an OAuth authorization flow is vulnerable to CSRF, allowing an attacker to bind their own account to a victim's session.

Fix: Generate a random state value per request, store it server-side or in a signed cookie, and verify it on callback before exchanging the authorization code.

Payments

PAYMENT_STRIPE_WEBHOOK_SIGNATURE_MISSING

critical

Risk: Attackers may forge payment events and unlock paid features or alter subscription state.

Fix: Use stripe.webhooks.constructEvent with the raw request body and webhook signing secret before processing events.

PAYMENT_IDEMPOTENCY_MISSING

high

Risk: Repeated webhook delivery can duplicate side effects, corrupt subscription state, or issue duplicate credits.

Fix: Store processed event IDs and make subscription updates idempotent.

STRIPE_CLIENT_TRUSTED_AMOUNT

critical

Risk: If a checkout or payment-intent handler reads the amount or price directly from the request body, a user can tamper with it client-side and pay any amount they choose.

Fix: Always look up the price/amount server-side from a fixed price ID or your own product catalog — never trust a client-submitted amount.

Privacy

PRIVACY_DATA_COLLECTION_FOUND

medium

Risk: Collected personal data, AI prompts, analytics, and payment metadata need clear privacy policy disclosure and retention controls.

Fix: Review the generated data inventory and publish a lawyer-reviewed privacy policy before public launch.

PRIVACY_NO_DELETION_ENDPOINT

medium

Risk: GDPR, CCPA, and similar regulations require a way for users to request deletion of their personal data; without one, the app cannot honor erasure requests.

Fix: Add an account deletion flow (self-service or support-triggered) that removes or anonymizes personal data across all data stores.

PRIVACY_THIRD_PARTY_TRACKING_NO_CONSENT

medium

Risk: Loading analytics, ads, or session-replay scripts before obtaining consent can violate GDPR/ePrivacy and similar cookie-consent requirements.

Fix: Gate non-essential tracking scripts behind a cookie consent banner and only load them after opt-in where required.

Secrets

SECRETS_ENV_COMMITTED

critical

Risk: Committed environment files can leak production credentials and third-party API keys.

Fix: Remove real .env files from version control, rotate exposed secrets, and keep only .env.example committed.

SECRETS_HARDCODED

critical

Risk: Hardcoded keys can be extracted from source code, logs, client bundles, or repository history.

Fix: Move secrets to server-side environment variables, rotate exposed keys, and add secret scanning to CI.

SECRETS_FRONTEND_PUBLIC_KEY

critical

Risk: Secrets in NEXT_PUBLIC_* variables or client components can be exposed to every browser user.

Fix: Never expose OpenAI, Stripe secret, Supabase service role, or private API keys to frontend code. Move calls server-side or behind an authenticated proxy.

CI_SECRETS_HARDCODED_IN_WORKFLOW

critical

Risk: Secrets committed inside a GitHub Actions or other CI workflow file are visible to anyone with repository read access and remain in git history even after removal.

Fix: Reference secrets only through the CI provider's encrypted secret store (e.g. ${{ secrets.NAME }}) and rotate any value that was ever hardcoded.

HARDCODED_CLOUD_CREDENTIAL

critical

Risk: An AWS access key (or similar cloud credential) committed to source code grants direct access to cloud infrastructure and is routinely scraped by automated bots within minutes of a public push.

Fix: Remove the credential, rotate it immediately in the cloud provider console, and use environment variables or a secrets manager instead.

EXPOSED_BACKUP_FILE

high

Risk: .bak, .old, .backup, or ad-hoc .sql dump files often contain full database contents or old credentials, and are easy to overlook when reviewing what's committed.

Fix: Remove backup/dump files from version control and store backups outside the repository with proper access controls.

SSRF

SSRF_UNVALIDATED_URL_FETCH

high

Risk: Fetching a URL taken directly from request input lets an attacker make the server call internal services, cloud metadata endpoints, or arbitrary hosts.

Fix: Validate outbound URLs against an allowlist of hosts/protocols, block private/link-local IP ranges, and avoid following redirects blindly.

File Upload

UPLOAD_UNRESTRICTED_FILE_TYPE

high

Risk: Accepting any file type or size lets attackers upload executable scripts, oversized payloads, or files that trigger downstream parser vulnerabilities.

Fix: Validate MIME type and extension against an allowlist, enforce a maximum file size, and store uploads outside the web root or in object storage with restricted execution.

UPLOAD_PATH_TRAVERSAL

critical

Risk: Writing a file using an attacker-supplied filename or path can overwrite arbitrary files via ../ traversal.

Fix: Generate a server-side random filename, strip path separators, and write only inside a fixed, dedicated upload directory.

WebSocket

WEBSOCKET_NO_AUTH

high

Risk: An unauthenticated WebSocket connection can let any client subscribe to real-time data or trigger actions meant for authenticated users only.

Fix: Verify a session or token on connection (and on reconnection) before accepting subscriptions or forwarding messages.

XSS

XSS_UNSAFE_HTML

high

Risk: Rendering user-controlled HTML without sanitization can execute attacker-controlled scripts.

Fix: Avoid raw HTML rendering. If required, sanitize with a proven HTML sanitizer and use a strict CSP.
